# Module 5 — RAG & Grounding: ทำให้ AI ตอบจาก "ข้อมูลจริงของลูกค้า"

⏱️ **40 ชั่วโมง (สัปดาห์ 12–15)** · 🎯 ผลลัพธ์: RAG service บนเอกสารจริง + รายงานคุณภาพ retrieval

> RAG (Retrieval-Augmented Generation) เป็นงานที่ FDE ทำมากที่สุดในโลกจริง
> เพราะปัญหาที่ลูกค้าจ่ายเงินแก้คือ: "AI ตอบผิดเพราะไม่รู้ข้อมูลเรา"

---

## 5.1 RAG ทำงานอย่างไร (ภาพเดียวจบ)

```
INDEXING (ทำครั้งเดียว / เมื่อเอกสารเปลี่ยน)
┌──────────┐   ┌──────────┐   ┌───────────┐   ┌─────────────┐
│ เอกสาร    │──▶│ แตก chunk │──▶│  Embed     │──▶│  Vector DB  │
│ PDF/HTML │   │ + metadata│   │  → vector  │   │ + full-text │
└──────────┘   └──────────┘   └───────────┘   └─────────────┘

QUERY TIME (ทุกครั้งที่ผู้ใช้ถาม)
┌────────┐   ┌──────────┐   ┌──────────────┐   ┌────────┐   ┌────────┐
│ คำถาม  │──▶│ Embed    │──▶│ Retrieve top-k│──▶│ Rerank │──▶│  LLM   │
│        │   │ query    │   │ (+ BM25/filter)│  │        │   │ + cites│
└────────┘   └──────────┘   └──────────────┘   └────────┘   └────────┘
```

> 🔑 **ความจริงที่ต้องจำ:** ปัญหา RAG 90% ไม่ได้อยู่ที่ LLM แต่อยู่ที่ **retrieval**
> ถ้า retrieve ไม่เจอ คำตอบที่ดีที่สุดก็ตอบไม่ได้ — ต้องวัด retrieval ก่อนวัดคำตอบ

---

## 5.2 Chunking — จุดที่คนพลาดมากที่สุด

| วิธี | ข้อดี | ข้อเสีย | เหมาะกับ |
|---|---|---|---|
| **Fixed-size (เช่น 800 token, overlap 100)** | ง่าย ทำเร็ว | ตัดกลางประโยค/ตาราง | baseline |
| **Recursive (ตาม heading → paragraph)** | เกาะโครงสร้าง | ต้องพึ่งคุณภาพเอกสาร | คู่มือ, policy |
| **Semantic** | กลุ่มความหมายดี | แพง, ช้า, คาดเดายาก | บทความยาว |
| **Per-document / per-section** | context ครบ | chunk ใหญ่ เปลือง token | สัญญา, ระเบียบ |
| **Parent-child** (retrieve ย่อย, ส่ง parent ให้ LLM) | ดีที่สุดในหลายงาน | ซับซ้อน | เอกสารกฎหมาย/เทคนิค |
| **Table-aware** | ไม่ทำตารางพัง | ต้องแยก parse | รายงานการเงิน |

### Metadata ที่ต้องใส่ทุก chunk
```json
{
  "chunk_id": "policy-hr-2026-03#p12",
  "doc_id": "policy-hr-2026-03",
  "title": "ระเบียบการลาหยุด 2569",
  "section": "3.2 การลาคลอด",
  "effective_date": "2026-01-01",
  "department": "HR",
  "classification": "internal",
  "page": 12,
  "source_url": "https://...",
  "lang": "th"
}
```

> **metadata = สิทธิ์ + ความสด + ความน่าเชื่อถือ** สามอย่างนี้คือสิ่งที่ทำให้ RAG ใช้ในองค์กรได้จริง
> (เช่น "ห้าม retrieve เอกสารที่ผู้ใช้ไม่มีสิทธิ์" และ "ใช้เฉพาะฉบับที่ยังมีผลบังคับใช้")

## 5.3 Retrieval ที่ดีกว่านั้น

```
Hybrid search = vector search + BM25 (keyword)
                ↓
Metadata filter (สิทธิ์, วันที่, แผนก)
                ↓
Reranker (cross-encoder หรือ LLM rerank)
                ↓
top-k สุดท้าย (3–8 chunk)
```

**ทำไมต้อง hybrid:** vector เก่งเรื่องความหมาย แต่พลาดรหัส/ชื่อเฉพาะ ("สัญญาเลขที่ A-2026/117")
ส่วน BM25 เก่งตรงนั้น → ใช้คู่กันได้ผลดีที่สุดในงานจริง

**ทำไมต้องมี rerank:** vector search เร็วแต่หยาบ → ดึง 50 ตัวมาก่อน แล้ว rerank เหลือ 5 ตัว
→ คุณภาพเพิ่มชัดเจนด้วยต้นทุนต่ำ

## 5.4 ตอนสร้างคำตอบ (generation)

```python
SYSTEM = """คุณคือผู้ช่วยตอบคำถามจากเอกสารภายในองค์กร
กฎ:
1. ตอบจาก <context> เท่านั้น ถ้าไม่พบให้ตอบ "ไม่พบข้อมูลในเอกสารที่ให้มา"
2. อ้างอิงทุกข้อความด้วย [doc_id#section]
3. ห้ามเปิดเผยข้อมูลนอกเหนือจากที่ถาม
4. ถ้าคำถามคลุมเครือ ให้ถามกลับ 1 คำถาม"""

USER = f"""<context>
{'\n\n'.join(f"[{c['doc_id']}#{c['section']}] {c['text']}" for c in chunks)}
</context>

คำถาม: {question}"""
```

**สิ่งที่ต้องมีเสมอ:**
- **Citation** — ผู้ใช้ต้องตรวจสอบได้ (และนี่คือสิ่งที่ทำให้ผู้ใช้เชื่อถือ)
- **"ไม่พบข้อมูล"** — ปฏิเสธได้คือฟีเจอร์ ไม่ใช่ความล้มเหลว
- **แสดงแหล่งที่มา** ใน UI พร้อมลิงก์

## 5.5 วัดคุณภาพ RAG (แยก 2 ชั้น!)

### ชั้นที่ 1: Retrieval quality
| Metric | นิยาม | เป้าเริ่มต้น |
|---|---|---|
| **Recall@k** | chunk ที่ถูกต้องอยู่ใน top-k กี่ % | ≥ 0.85 (k=5) |
| **Precision@k** | top-k มีของเสียกี่ % | ≥ 0.6 |
| **MRR** | อันดับของ chunk ที่ถูกอยู่ที่เท่าไร | ≥ 0.7 |
| **Hit rate** | มี chunk ที่ถูกอย่างน้อย 1 ตัวไหม | ≥ 0.95 |

### ชั้นที่ 2: Answer quality
| Metric | วิธีวัด |
|---|---|
| **Faithfulness / groundedness** | คำตอบมีที่มาจาก context จริงไหม (ตรวจด้วย LLM judge + คนสุ่มตรวจ) |
| **Answer relevance** | ตอบตรงคำถามไหม |
| **Completeness** | ครบทุกส่วนที่ควรตอบไหม |
| **Abstention correctness** | เมื่อไม่มีข้อมูล ตอบ "ไม่พบ" ถูกต้องไหม |
| **Citation accuracy** | citation ชี้ไปยังที่ถูกจริงไหม |

> ⚠️ **ห้ามวัดแค่ "คำตอบดูดีไหม"** — ต้องมี golden set ที่คนยืนยันแล้ว
> และต้องวัด retrieval แยกจาก generation เพื่อรู้ว่าต้องแก้ตรงไหน

### Golden set เริ่มต้น (ทำใน 2 ชม.)
```jsonl
{"question": "ลาคลอดได้กี่วัน", "expected_chunks": ["policy-hr-2026-03#3.2"], "expected_answer": "98 วัน"}
{"question": "สัญญาเลขที่ A-2026/117 หมดอายุเมื่อไร", "expected_chunks": ["contract-A-2026-117#2"], "expected_answer": "..."}
{"question": "Who is the CEO of X?", "expected_chunks": [], "expected_answer": "ไม่พบข้อมูล"}
```
**เป้า:** 30–50 ข้อ ครอบคลุม: คำถามตรง, คำถามอ้อม, คำถามที่ไม่มีคำตอบ, คำถามภาษาไทยผสมอังกฤษ,
คำถามที่ต้องใช้หลายเอกสาร

## 5.6 RAG ในโลกจริง: เรื่องที่เจอเฉพาะองค์กร

| ปัญหา | ตัวอย่างจริง | ทางแก้ |
|---|---|---|
| **เอกสารสแกน** | PDF สแกน ไม่มี text layer | OCR ก่อน + เก็บ confidence |
| **ตารางซับซ้อน** | งบการเงินหลายระดับ | parse เป็น structured (HTML/markdown table) |
| **เวอร์ชันซ้อน** | ระเบียบปี 2565 และ 2569 พร้อมกัน | `effective_date` filter + แจ้งผู้ใช้ |
| **สิทธิ์** | พนักงานทั่วไปไม่ควรเห็นเงินเดือน | filter ตาม ACL ก่อน search (สำคัญมาก) |
| **ภาษาไทย** | chunk แล้วตัดกลางคำ, embedding ไทยอ่อนกว่า | chunk ตามประโยค, ทดสอบ embedding หลายตัว |
| **ข้อมูลสด** | ราคาสินค้าเปลี่ยนทุกชั่วโมง | แยก RAG (ความรู้) ออกจาก API (ข้อมูลสด) |
| **เอกสารโตไม่หยุด** | เพิ่มวันละ 500 ไฟล์ | incremental indexing + ตาราง check ว่า index ล่าสุดเมื่อไร |

> 🔑 **หลักคิด:** "RAG สำหรับความรู้ที่นิ่ง + API สำหรับข้อมูลสด" — อย่าใช้ RAG แก้ปัญหาทุกอย่าง

## 5.7 Lab (สัปดาห์ 12–15)

### Lab 5.1 (8 ชม.) — Baseline RAG
- เลือกเอกสารจริง 20–50 ไฟล์ (คู่มือบริษัท, ระเบียบ, docs ของ open source)
- ทำ pipeline: parse → chunk → embed → store (ใช้ pgvector หรือ Chroma)
- ทำ query CLI: ถาม → ได้คำตอบ + citation
- วัด: Recall@5, hit rate บน golden set 30 ข้อ

### Lab 5.2 (10 ชม.) — ปรับปรุงและวัดผล ★
ทดลองอย่างน้อย 3 การเปลี่ยนแปลง แล้ววัดทุกครั้ง:
1. เปลี่ยน chunking (เช่น 400/800/1200 token + overlap)
2. เพิ่ม hybrid search (vector + BM25)
3. เพิ่ม reranker
4. เพิ่ม metadata filter
บันทึกเป็นตาราง: การทดลอง → Recall@5 → latency → ต้นทุน → ข้อสรุป

### Lab 5.3 (8 ชม.) — Golden set & error analysis
- สร้าง golden set 30–50 ข้อ (รวม 5 ข้อที่ไม่มีคำตอบ)
- จำแนก error: retrieval ผิด / chunk ไม่มีข้อมูล / LLM อ่านผิด / คำถามกำกวม
- เขียน "top 5 สาเหตุที่ระบบพัง" พร้อมจำนวนเคส

### Lab 5.4 (6 ชม.) — RAG ที่มีสิทธิ์
- ใส่ ACL ใน metadata
- ทดสอบว่า user A ไม่สามารถ retrieve เอกสารของ user B ได้
- เขียนคำอธิบายวิธีทำใน design doc (ใช้ต่อ Module 9)

### Lab 5.5 (8 ชม.) — ข้อสอบปากเปล่า
อธิบายให้ "ผู้บริหารที่ไม่เทคนิค" ฟังใน 5 นาที:
- RAG คืออะไร ทำไมไม่ใช้แค่แชท
- คุณภาพตอนนี้เป็นอย่างไร (ตัวเลข)
- ข้อจำกัดคืออะไร และจะจัดการอย่างไร
อัดเสียงหรือเขียนสคริปต์ไว้
