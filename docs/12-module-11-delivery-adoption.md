# Module 11 — Delivery & Adoption: ทำให้คนใช้จริง ★

⏱️ **35 ชั่วโมง (สัปดาห์ 32–35)** · 🎯 ผลลัพธ์: delivery plan + adoption metrics + ระบบที่มีผู้ใช้จริง

> **สถิติที่ต้องจำ:** งาน AI ส่วนใหญ่ที่ "ส่งมอบสำเร็จ" ไม่มีคนใช้
> การ deploy ไม่ใช่จุดจบ — **การที่คนเปลี่ยนวิธีทำงานคือจุดจบ**

---

## 11.1 Delivery model ที่ FDE ใช้จริง

```
Week 0-1    FRAME      problem statement, metric, stakeholder map
Week 2-3    PROVE      พิสูจน์สมมติฐานหลักด้วยของหยาบ (eval บนข้อมูลจริง 50 เคส)
Week 4-6    BUILD      vertical slice — 1 use case ครบวงจร ไม่ใช่ 5 อันครึ่ง ๆ
Week 7-8    PILOT      ผู้ใช้จริง 5–15 คน, feedback ทุกวัน
Week 9-10   HARDEN     security, monitoring, edge case, documentation
Week 11-12  SCALE      ขยายผู้ใช้, training, handover, วัดผล
```

**หลักการที่ห้ามละเมิด:**
1. **Vertical slice ก่อน horizontal** — ทำ 1 use case ให้จบ ดีกว่าทำ 5 อันค้าง
2. **ผู้ใช้จริงตั้งแต่สัปดาห์ที่ 7** — ถ้าเร็วกว่านี้ได้ ยิ่งดี
3. **ทุก sprint ต้องมี demo ที่ผู้ใช้กดเองได้** — ไม่ใช่สไลด์
4. **วัดผลก่อน-หลัง** — baseline ต้องเก็บก่อนสร้าง

---

## 11.2 Milestone ที่ต้องมีเกณฑ์ผ่านชัดเจน

| Milestone | เกณฑ์ผ่าน | ใครเซ็น |
|---|---|---|
| **M1: Problem validated** | ตัวเลข baseline + target ตกลงแล้ว | business owner |
| **M2: Feasibility proven** | eval บนข้อมูลจริง ≥50 เคส ถึงเป้า (หรือใกล้) | FDE + tech lead |
| **M3: Usable** | ผู้ใช้ 5 คนใช้งานได้โดยไม่ต้องมีคนช่วย | pilot users |
| **M4: Safe** | security review ผ่าน, monitoring ครบ | IT/CISO |
| **M5: Adopted** | ≥70% ของกลุ่มเป้าหมายใช้ ≥3 ครั้ง/สัปดาห์ ต่อเนื่อง 4 สัปดาห์ | business owner |
| **M6: Handover** | ทีมลูกค้าดูแลต่อได้, เอกสารครบ, runbook ทดสอบแล้ว | ops owner |

> ⚠️ **M5 คือ milestone ที่คนส่วนใหญ่ไม่ผ่าน** — และเป็นที่ที่ ROI จริงเกิด

## 11.3 Change Management สำหรับงาน AI (ส่วนที่คนเทคนิคเกลียดแต่ขาดไม่ได้)

### ทำไมคนไม่ใช้ระบบดี ๆ
| สาเหตุ | อาการ | ทางแก้ |
|---|---|---|
| กลัวถูกแทนที่ | ไม่ใช้/ใช้แบบขอไปที | สื่อสารชัดว่า "ลดงานซ้ำ ไม่ใช่ลดคน", ให้เขาเป็นคนออกแบบ workflow |
| ไม่เชื่อถือ AI | ตรวจทุกอย่างช้า ๆ | แสดง citation + ให้แก้ได้ + เริ่มจากงาน low-stakes |
| ยุ่งเกินไปจะเรียน | "ไว้ก่อน" | ฝังในเครื่องมือที่เขาใช้อยู่แล้ว (ไม่ต้องเปิดเว็บใหม่) |
| ไม่เห็นประโยชน์ | ใช้ครั้งเดียวเลิก | ทำให้เห็นเวลาที่ประหยัด (แสดง "คุณประหยัด 42 นาทีวันนี้") |
| ระบบช้า | รอแล้วรำคาญ | streaming + skeleton + background job |
| ผิดบ่อย | เลิกใช้หลังครั้งที่ 3 | eval + abstention + escalation ที่ดี |

### กลยุทธ์ adoption ที่ได้ผลจริง
1. **หา champion 2–3 คน** ที่ enthusiastic → ให้เขาเป็นคนสอนเพื่อน (peer > vendor)
2. **เริ่มจากคนที่งานหนักที่สุด** — เขาจะเห็นประโยชน์เร็วที่สุด
3. **ทำ workflow ให้เปลี่ยนน้อยที่สุด** — ถ้าต้องเปลี่ยน 5 ขั้น เขาไม่เปลี่ยน
4. **Publicize wins** — ตัวเลขจริงจาก champion ใน meeting
5. **ให้ทางออกเมื่อ AI ผิด** — ปุ่ม "ส่งต่อให้คน" ต้องชัดเจน
6. **วัดและประกาศทุกสัปดาห์** — transparency สร้างความเชื่อใจ

> 🔑 **FDE ต้องเป็น "คนของลูกค้า" ไม่ใช่ "คนของ vendor"**
> ถ้าทีมลูกค้ารู้สึกว่าคุณอยู่ข้างเขา adoption จะเพิ่มขึ้นแบบก้าวกระโดด

## 11.4 Adoption Metrics (ตัวเลขที่ต้องรายงานทุกสัปดาห์)

| Metric | นิยาม | เป้า |
|---|---|---|
| **Activation** | % กลุ่มเป้าหมายที่ลอง ≥1 ครั้ง | ≥80% ใน 4 สัปดาห์ |
| **Retention (W4)** | % ที่ยังใช้ในสัปดาห์ที่ 4 | ≥60% |
| **Frequency** | ครั้ง/คน/สัปดาห์ | ≥3 |
| **Depth** | % ของงานประเภทนั้นที่ผ่านระบบ | ≥50% |
| **Time saved** | ชั่วโมงที่ประหยัด/สัปดาห์ (วัดจริง ไม่ใช่เดา) | ตาม business case |
| **Override rate** | % ที่คนแก้คำตอบ AI | <30% (สูงกว่านี้ = คุณภาพยังไม่พอ) |
| **Escalation rate** | % ที่ส่งต่อคน | 10–25% |
| **Satisfaction** | 👍/👎 หรือ NPS ภายใน | ≥70% 👍 |
| **Support tickets** | ticket ที่เกิดจากระบบ | ลดลงเมื่อเวลาผ่านไป |

> 💡 **Time saved ต้องวัดจริง** — สุ่ม 10 งาน วัดเวลาก่อน/หลัง ไม่ใช่คำนวณจากความรู้สึก
> ถ้าคุณรายงานตัวเลขที่ CFO ตรวจสอบได้ คุณจะได้งานต่อทันที

## 11.5 Handover: สิ่งที่ทำให้คุณเป็น FDE ระดับ senior

**Handover ที่ดี = ลูกค้าดูแลต่อได้โดยไม่ต้องโทรหาคุณ**

```
handover/
├── 01-system-overview.md       # สถาปัตยกรรม + data flow
├── 02-runbook.md               # วิธีดูแลระบบ + แก้ปัญหาที่พบบ่อย
├── 03-architecture-decision-records/  # ADR: ทำไมเลือกแบบนี้
├── 04-eval-guide.md            # วิธีรัน eval + ตีความผล
├── 05-prompt-management.md     # วิธีแก้ prompt + ต้องรัน eval อะไร
├── 06-troubleshooting.md       # อาการ → สาเหตุ → วิธีแก้
├── 07-access-and-credentials.md# ใครมีสิทธิ์อะไร (ไม่ใส่รหัสจริง)
├── 08-cost-model.md            # ต้นทุน + วิธีคุม
├── 09-roadmap.md               # สิ่งที่ควรทำต่อ
└── 10-training/                # วิดีโอ/สไลด์/แบบฝึกหัดสำหรับผู้ใช้
```

**+ สิ่งที่คนมักลืม:**
- **บันทึกวิดีโอ 5 คลิปสั้น** (2–3 นาที) สอนงานหลัก
- **ระบุ owner ให้ชัดเจน** ในทีมลูกค้า
- **shadow 1 สัปดาห์** ให้คนที่จะดูแลต่อได้ลงมือจริงโดยคุณอยู่ข้าง ๆ
- **roadmap ต่อ** — ลูกค้าจะรู้สึกว่าระบบไม่ตายเมื่อคุณจากไป

> 🎓 **การ handover ที่ดีคือสิ่งที่ทำให้ลูกค้าเรียกคุณกลับมาทำงานรอบสอง**
> และเป็นแหล่ง referral ที่ดีที่สุดของ FDE

## 11.6 เมื่อโปรเจกต์กำลังจะล้มเหลว (สัญญาณเตือน)

| สัญญาณ | ความหมาย | ทำอะไร |
|---|---|---|
| ไม่มีใครใช้ในสัปดาห์ที่ 2 | ปัญหา adoption หรือคุณค่าไม่จริง | หยุดเพิ่มฟีเจอร์ → สัมภาษณ์ผู้ใช้ 5 คน |
| ผู้ใช้ override >50% | คุณภาพไม่พอ | กลับไปทำ eval + retrieval |
| ไม่มี baseline | วัดผลไม่ได้ | หยุด แล้วไปวัดก่อน (1 สัปดาห์) |
| scope โตทุกสัปดาห์ | ไม่มีเจ้าของ decision | บังคับ prioritized backlog + change control |
| IT ยังไม่อนุมัติในสัปดาห์ที่ 10 | ประเมิน security ช้าเกิน | เริ่ม security review ตั้งแต่สัปดาห์ที่ 1 |
| ไม่มี executive sponsor | จะตายเมื่อมีอุปสรรค | หา sponsor หรือพิจารณายุติ |

**การยุติโปรเจกต์อย่างมืออาชีพ** (ทำได้และควรทำ):
> "จาก eval 6 สัปดาห์ คุณภาพได้ 61% แต่เป้าคือ 85% และต้นทุนสูงกว่า manual
> ผมแนะนำให้หยุด และหันไปทำ X ที่มีข้อมูลดีกว่า — นี่คือรายงานสิ่งที่เราเรียนได้"
> **ลูกค้าจะจ้างคุณอีก** เพราะคุณซื่อสัตย์กับงบของเขา
