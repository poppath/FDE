# Module 13 — Capstone: ระบบจริง ผู้ใช้จริง ครบวงจร

⏱️ **60 ชั่วโมง (สัปดาห์ 41–48)** · 🎯 ผลลัพธ์: ระบบ live + case study ที่ใช้สมัครงานได้

> **หลักการ:** Capstone ของ FDE ไม่ใช่ "โปรเจกต์สวย ๆ" แต่คือ **หลักฐานว่าคุณทำงานครบวงจรได้**
> ต้องมี 4 อย่าง: ผู้ใช้จริง, ตัวเลขก่อน-หลัง, ระบบที่รันอยู่จริง, และสิ่งที่คุณเรียนรู้จากความล้มเหลว

## 13.1 เลือกโปรเจกต์ที่ใช่

ใช้ **baseline project** ที่คุณเขียนไว้ใน Module 0 — ถ้าไม่มี ให้เลือกจาก:

| แบบ | เหมาะกับ | ตัวอย่าง |
|---|---|---|
| **A. ในงานปัจจุบัน** ★ดีที่สุด | มีคนทำงานอยู่แล้ว | ระบบช่วยตอบคำถาม HR, สรุปสัญญา, จัดหมวด ticket |
| **B. องค์กร/NGO ที่รู้จัก** | อยากได้ผู้ใช้จริง | ระบบตอบคำถามนโยบาย, ช่วยเขียน grant proposal |
| **C. โอเพนซอร์ส / ชุมชน** | ไม่มีเวลาไปหาลูกค้า | RAG บนเอกสารกฎหมายไทย, ผู้ช่วยตอบ FAQ โรงพยาบาล |
| **D. ธุรกิจของครอบครัว/ตัวเอง** | หาลูกค้ายาก | ร้านค้าออนไลน์: ตอบแชท, สรุปรีวิว |

**เกณฑ์คัดเลือก (ต้องได้ ≥4/6):**
- [ ] มีผู้ใช้จริง ≥5 คนที่ใช้ต่อเนื่องได้
- [ ] มี baseline ที่วัดได้ (เวลาหรือจำนวน)
- [ ] ข้อมูลจริง (เอกสารจริง ไม่ใช่ sample)
- [ ] อยู่ใน vertical ที่คุณเลือก
- [ ] ทำได้ใน 8 สัปดาห์คนเดียว
- [ ] ไม่ต้องอนุมัติงบ

## 13.2 กำหนดขอบเขต (สำคัญที่สุด)

**ทำ 1 use case ให้ครบ ดีกว่า 5 อันค้าง**

```
ตัวอย่างขอบเขตที่ดี:
"ผู้ช่วยตอบคำถามระเบียบการลาหยุดสำหรับพนักงาน 1,200 คน
 - รองรับ 1 โดเมน: ระเบียบ HR เท่านั้น
 - ตอบพร้อม citation + ลิงก์เอกสารต้นฉบับ
 - ถ้าไม่มั่นใจ → ส่งต่อ HR (ไม่เดา)
 - ใช้ผ่าน LINE OA หรือเว็บภายใน
 - เป้า: ลดเวลาได้รับคำตอบจาก 6 ชม. → <5 นาที, 70% ของคำถาม"

ตัวอย่างขอบเขตที่แย่:
"AI assistant ที่ช่วยได้ทุกเรื่องของ HR"  ← ไม่มีทางจบ
```

## 13.3 Timeline 8 สัปดาห์

| สัปดาห์ | งาน | Artifact |
|---|---|---|
| 1 | Discovery (shadow + สัมภาษณ์ + วัด baseline) | problem statement + opportunity assessment |
| 2 | Design doc + สมมติฐานที่ต้องพิสูจน์ | design doc (ส่งให้เพื่อน review) |
| 3 | Feasibility spike: eval บนข้อมูลจริง 50 เคส | ตาราง eval แรก (อาจยังไม่ถึงเป้า!) |
| 4 | Build vertical slice | demo ที่ผู้ใช้กดได้ |
| 5 | Pilot 5 คน + feedback ทุกวัน | pilot report |
| 6 | Hardening: security, guardrail, monitoring | security pack (ย่อ) |
| 7 | ขยายผู้ใช้ + training + handover pack | handover + adoption dashboard |
| 8 | วัดผล + case study + พิตช์ | case study + สไลด์ |

> ⚠️ **สัปดาห์ 3 คือจุดตัดสิน**: ถ้า eval ออกมาแย่ ให้เลือก
> (ก) ปรับขอบเขตให้เล็กลง (ข) เปลี่ยนข้อมูล (ค) เปลี่ยนวิธี (ไม่ใช่เพิ่ม prompt มั่ว ๆ)

## 13.4 สิ่งที่ต้องส่ง (Definition of Done)

### 1. ระบบที่รันจริง
- [ ] URL ที่เข้าถึงได้ (หรือวิดีโอ demo ถ้าเป็นภายใน)
- [ ] ผ่าน eval gate บน golden set ≥50 เคส
- [ ] มี guardrails + audit log
- [ ] มี monitoring + runbook

### 2. หลักฐานผลลัพธ์
- [ ] Baseline vs after (ตัวเลขจริง)
- [ ] Adoption metrics 4 สัปดาห์
- [ ] คำพูดของผู้ใช้จริง ≥3 คน (quote)
- [ ] Error analysis: ระบบพังเพราะอะไร + แก้อย่างไร

### 3. Case study (2–4 หน้า)
```
1. บริบท: ลูกค้า/องค์กรคืออะไร มีปัญหาอะไร (ตัวเลข)
2. สิ่งที่ค้นพบใน discovery (2–3 insight ที่ไม่คาดคิด)
3. ทางแก้ + ทำไมเลือกแบบนี้
4. ผลลัพธ์ (ตัวเลข before/after)
5. สิ่งที่พลาดและแก้อย่างไร ← ส่วนที่ทำให้คุณน่าเชื่อถือที่สุด
6. สิ่งที่ทำต่อ
7. สถาปัตยกรรม + eval result (ภาคผนวก)
```

### 4. Repo ที่สะอาด
- [ ] README ที่คนอื่นรันตามได้ใน 5 นาที
- [ ] architecture diagram
- [ ] ADR (Architecture Decision Records) 3–5 ข้อ
- [ ] test + eval + CI ทำงาน
- [ ] ไม่มี secret ใน Git

## 13.5 ตัวอย่าง Case Study ที่ดี (โครง)

```
## ลดเวลาตอบคำถาม HR จาก 6 ชั่วโมงเหลือ 3 นาที
### ที่บริษัท X (1,200 พนักงาน, 8 สาขา)

**ปัญหา**
ทีม HR 3 คนตอบคำถามซ้ำ 320 ครั้ง/เดือน (60% เป็น 8 คำถามเดิม)
พนักงานรอเฉลี่ย 6 ชม. และ 22% ถามซ้ำเพราะไม่ได้รับคำตอบ

**สิ่งที่ค้นพบ**
1. ปัญหาไม่ใช่ "ไม่มีระบบ" แต่คือ "ระเบียบมี 14 ฉบับ หลายฉบับถูกแทนที่แล้ว"
   → 30% ของคำตอบที่ HR ตอบเองอ้างฉบับที่หมดอายุ
2. คนไม่กล้าใช้ AI กับเรื่องเงิน/วันลา → ต้องมี citation เสมอ
3. ช่องทางสำคัญคือ LINE ไม่ใช่เว็บ → ต้องอยู่ในที่ที่เขาใช้อยู่แล้ว

**ทางแก้**
RAG บนระเบียบ 14 ฉบับ + effective_date filter + citation + escalation
เริ่มจาก 1 โดเมน (การลา) ไม่ทำทุกเรื่อง

**ผลลัพธ์ (8 สัปดาห์)**
- เวลาตอบเฉลี่ย: 6 ชม. → 3 นาที (p50)
- คำถามที่ AI ตอบได้โดยไม่ต้อง escalate: 68%
- HR saved: 21 ชม./เดือน (วัดจริงจาก log)
- ความถูกต้องของ citation: 96% (สุ่มตรวจ 100 ครั้ง)
- adoption: 74% ของพนักงานใน 4 สัปดาห์

**สิ่งที่พลาด**
- สัปดาห์ที่ 3: eval ได้แค่ 61% เพราะ chunking ตัดตารางวันลาพิเศษ
  → แก้ด้วย table-aware chunking → 84%
- สัปดาห์ที่ 5: ผู้ใช้ไม่ไว้ใจเพราะไม่มีปุ่ม "ดูเอกสารต้นฉบับ"
  → เพิ่ม + 👎 ลดจาก 31% → 9%
- ไม่ได้เตรียมตัวเรื่อง PDPA ตั้งแต่ต้น ทำให้ security review ช้า 1 สัปดาห์
```

## 13.6 Rubric ให้คะแนนตัวเอง (เต็ม 100)

| มิติ | น้ำหนัก | เกณฑ์ 5 คะแนน |
|---|---|---|
| Problem framing | 15 | มีตัวเลข baseline + target + constraint ชัด |
| Technical build | 20 | ระบบรันจริง มี test + eval + guardrail + monitoring |
| AI quality | 20 | eval ≥50 เคส, ผลดี, มี error analysis |
| Deployment/security | 15 | security pack, RBAC, log, runbook |
| Adoption | 15 | ≥5 ผู้ใช้จริง, metric 4 สัปดาห์, handover |
| Commercial | 10 | ROI คำนวณจริง, business case, พิตช์ผ่าน |
| Storytelling | 5 | case study อ่านแล้วเข้าใจใน 5 นาที |

**เกณฑ์:** ≥80 = พร้อมสมัคร FDE · 65–79 = พร้อมสมัครตำแหน่ง adjacent แล้วโตในงาน · <65 = ทำเพิ่ม 4 สัปดาห์
